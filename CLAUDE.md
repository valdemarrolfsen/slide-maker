# slide-maker

A pnpm-managed package: a local slide deck studio driven from Claude Code. Users write
slides as JSX, review them in a browser, and comment on the text to send feedback
back to Claude.

This file is for working on **the package**. Each generated deck gets its own
`CLAUDE.md`, written by `src/cli/scaffold.js`, which is what Claude reads when
working on a deck rather than on this codebase.

## Commands

```bash
pnpm demo             # studio on examples/demo
pnpm demo:build       # static build of it
pnpm typecheck        # typecheck
pnpm types            # generate published .d.ts (runs on npm pack)

node bin/slide-maker.js export examples/demo -f png -o ../../.preview
```

There is no build step for development. Node-side code is plain ESM JavaScript,
the viewer is TypeScript compiled by Vite on demand.

## Architecture

A deck directory contains only content: `deck.json`, `template.css`,
`slides/*.tsx`, `assets/`.
All machinery lives in this package. Vite's root is `src/viewer/`, and the deck
is pulled in through two virtual modules generated by `src/vite/plugin-deck.js`:

- `virtual:slide-maker/deck` emits a static import per slide file plus the config
- `virtual:slide-maker/style` imports `runtime.css`, the active `style.css`, then
  the deck's template-owned `template.css`
- `virtual:slide-maker/default-slides` emits imports for the current template's
  curated Add slide gallery. Only `Studio.tsx` imports it, so exported decks
  carry none of it

`slide-maker/runtime` is aliased to an absolute path, so a deck resolves it
whether the package is installed globally, run through pnpm dlx, or linked.

The comment API is middleware on the dev server, and comment changes are pushed
to the studio over Vite's existing HMR socket rather than a second websocket.

## Three concepts

A **template** is a complete starter presentation under `templates/<name>/`.
Its `template.json` names the default style, available default slides, and
guidance; `slides/` contains the deck copied by `init`; and optional
`template.css` contains its bespoke composition rules. Both slides and layout
are copied into the initialized deck.

A **style** is a visual design system: `styles/<name>/style.json` plus a
`style.css` of tokens, typography, and shared component treatments. It must not
contain selectors belonging to a particular template deck. A deck wears one,
named in `deck.json`.

A **default slide** is one reusable layout: `default_slides/<name>/default_slide.json`
plus `slide.tsx`. Default slides carry no colour, so any of them renders in any
style. Claude reads them through `list_default_slides` and
`read_default_slide`; Studio previews the current template's curated subset.

Analytical layouts can use the runtime's `BarChart`, `LineChart`,
`StackedBarChart`, `WaterfallChart`, `BubbleMatrix`, and `DataTable`
components. Keep the data and structure in JSX; let the active style own their
visual treatment.

The previews are the default-slide components rendered small, not screenshots. That
works because the studio has already loaded the deck's stylesheet, so anything
mounted in the page wears it: the gallery restyles with the deck for free, and
cannot drift out of date with what a slide would actually look like.

Styles and default slides are shadowed by deck-local copies in `styles/` and
`default_slides/`, so a project can fork a built-in by keeping its name.

## The user's slide-maker home

`~/.slide-maker/` (moveable with `SLIDE_MAKER_HOME`) holds `config.json` plus
`templates/`, `styles/` and `default_slides/` the user owns. It is the middle
tier of resolution everywhere: built-in, then home, then deck-local. That tier
is the whole point of a custom template. A brand belongs to the person, not to
the deck that happened to prompt it, so `create_custom_template` scaffolds into
the home directory and never into the current deck.

`src/core/custom-template.js` scaffolds and returns a brief; it does not
generate a design. Crafting a template means reading a source project and
writing CSS, which Claude does with its own file tools, and a generator here
would be a second, worse way to edit a file. The scaffold forks a built-in style
so every `--sm-*` token is present to overwrite rather than remembered.

Because a style can now live outside both the package and the deck, Vite's
`server.fs.allow` includes the home directory. Without it the studio 403s on a
stylesheet the deck legitimately wears.

## Invariants

**The runtime owns shared structure, templates own bespoke composition, and
styles own looks.** No colour or font family belongs in a template stylesheet;
it consumes the active style's `--sm-*` tokens and inherited typography.
Conversely, no template-specific selector belongs in a style. This is what lets
a consulting exhibit or sales dashboard keep its geometry while changing the
deck's palette and typography. The same rule binds default slides: one that
hard-codes a colour stops being renderable in every style.

**Slides are a fixed 1280x720 canvas, scaled with a transform, never reflowed.**
This is what makes the studio, the static build and the PDF pixel-identical, and
what keeps comment anchors valid at any zoom.

**The slides directory is watched, not just the slide files.** Vite only
watches what the module graph already imports, and the case that has to work is
a file that does not exist yet: adding one is how a deck grows, whoever is
writing it. `plugin-deck.js` adds the directory itself to the watcher, and
without that a new slide never appears, not even on a manual refresh.

**Comments are a file, not a service.** `.slide-maker/comments.json` is the
single source of truth, written atomically via temp file and rename. The studio
and the MCP server are separate processes and neither requires the other.

**A built deck is one file.** `src/vite/plugin-singlefile.js` inlines the script
and styles and builds an IIFE rather than a module, because browsers refuse to
load module scripts over `file://`. Three things there are load-bearing and easy
to undo by accident: the inlined script must go at the end of `<body>` (a classic
script is not deferred), the `</body>` splice must use a function replacement
(bundled React is full of `$` sequences that a string replacement mangles), and
closing tags inside inlined content must be escaped.

**CSS specificity is load-bearing.** Runtime rules are single-class so style
rules win on order. The element reset is wrapped in `:where()` to carry zero
specificity; unwrapping it silently eats every component margin. Anything that
must beat a runtime rule gets a comment saying so.

## MCP surface

`src/mcp/server.js` is deliberately read-mostly. Claude edits slide files with
its own file tools; duplicating that here would create two ways to do one thing.
What MCP provides is the review state Claude cannot otherwise reach: open
comments and the text they point at, the style and default-slide registries,
and `render_slide` so Claude can look at what it built. `read_default_slide` returns JSX
for Claude to copy rather than writing a file, for the same reason.

`create_custom_template` is the one tool that writes outside the deck, because
the directory it writes to is not something Claude can be expected to guess.
It returns the crafting brief and stops there.

## Conventions

- ESM only.
- No em dashes in comments, docs or UI copy.
- Comments explain why, not what.
- Keep dependencies few.
