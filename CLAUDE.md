# slide-maker

A pnpm-managed package: a local slide deck studio driven from Claude Code. Users write
slides as JSX, review them in a browser, and comment on the text to send feedback
back to Claude.

This file is for working on **the package**. Each generated deck gets its own
`CLAUDE.md`, written by `src/cli/scaffold.js`, which is what Claude reads when
working on a deck rather than on this codebase.

## Commands

```bash
pnpm demo             # studio on examples/demo
pnpm demo:build       # static build of it
pnpm typecheck        # typecheck
pnpm types            # generate published .d.ts (runs on npm pack)

node bin/slide-maker.js export examples/demo -f png -o ../../.preview
```

There is no build step for development. Node-side code is plain ESM JavaScript,
the viewer is TypeScript compiled by Vite on demand.

## Architecture

A deck directory contains only content: `deck.json`, `slides/*.tsx`, `assets/`.
All machinery lives in this package. Vite's root is `src/viewer/`, and the deck
is pulled in through two virtual modules generated by `src/vite/plugin-deck.js`:

- `virtual:slide-maker/deck` emits a static import per slide file plus the config
- `virtual:slide-maker/style` imports `runtime.css` then the active `style.css`

`slide-maker/runtime` is aliased to an absolute path, so a deck resolves it
whether the package is installed globally, run through pnpm dlx, or linked.

The comment API is middleware on the dev server, and comment changes are pushed
to the studio over Vite's existing HMR socket rather than a second websocket.

## Two words

A **style** is a design system: `styles/<name>/style.json` plus a `style.css`
of tokens. A deck wears one, named in `deck.json`.

A **template** is one slide: `templates/<name>/template.json` plus a
`slide.tsx` written against the runtime. Templates carry no colour, so any
template renders in any style.

Templates are aimed at Claude working inside a deck, not at the person running
`init`. `init` asks only for a style and seeds a cover; which layout a slide
wants is decided while writing it, through `list_templates` and
`read_template`. The studio's Add slide picker is the same library from the
other side: it copies a template into `slides/` with its example copy intact,
for the user to then brief Claude on.

Both are shadowed by deck-local copies in `styles/` and `templates/` inside the
deck, so a project can fork a built-in by keeping its name.

## Invariants

**The runtime owns structure, styles own looks.** No colour or font size
belongs in `src/runtime/`. A style that needs a new structural element means
adding it to the runtime so every style can dress it. The same rule binds
templates: a template that hard-codes a colour stops being renderable in every
style, which is the only thing that makes the library worth having.

**Slides are a fixed 1280x720 canvas, scaled with a transform, never reflowed.**
This is what makes the studio, the static build and the PDF pixel-identical, and
what keeps comment anchors valid at any zoom.

**The slides directory is watched, not just the slide files.** Vite only
watches what the module graph already imports, and the case that has to work is
a file that does not exist yet: adding one is how a deck grows, whoever is
writing it. `plugin-deck.js` adds the directory itself to the watcher, and
without that a new slide never appears, not even on a manual refresh.

**Comments are a file, not a service.** `.slide-maker/comments.json` is the
single source of truth, written atomically via temp file and rename. The studio
and the MCP server are separate processes and neither requires the other.

**A built deck is one file.** `src/vite/plugin-singlefile.js` inlines the script
and styles and builds an IIFE rather than a module, because browsers refuse to
load module scripts over `file://`. Three things there are load-bearing and easy
to undo by accident: the inlined script must go at the end of `<body>` (a classic
script is not deferred), the `</body>` splice must use a function replacement
(bundled React is full of `$` sequences that a string replacement mangles), and
closing tags inside inlined content must be escaped.

**CSS specificity is load-bearing.** Runtime rules are single-class so style
rules win on order. The element reset is wrapped in `:where()` to carry zero
specificity; unwrapping it silently eats every component margin. Anything that
must beat a runtime rule gets a comment saying so.

## MCP surface

`src/mcp/server.js` is deliberately read-mostly. Claude edits slide files with
its own file tools; duplicating that here would create two ways to do one thing.
What MCP provides is the review state Claude cannot otherwise reach: open
comments and the text they point at, the style and template registries, and
`render_slide` so Claude can look at what it built. `read_template` returns JSX
for Claude to copy rather than writing a file, for the same reason.

## Conventions

- ESM only.
- No em dashes in comments, docs or UI copy.
- Comments explain why, not what.
- Keep dependencies few.
